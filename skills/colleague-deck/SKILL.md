# Their deck goes back the way it came

A deck from a colleague is not ours to rebuild. They will open it, look for
their own slides, and notice anything that moved. So nothing here regenerates
the file: every change is a zip rewritten to a zip, copying the bytes of every
part it was not asked to touch. A slide nobody edited comes back **byte-for-byte
identical**, and `tools/pptx_diff.py` proves that rather than asserting it.

That rules out the obvious tool. python-pptx re-serialises every part it parses,
so even an untouched slide comes out with different bytes — and on a deck
carrying a sensitivity label or SharePoint metadata it can drop parts it has no
class for. All the tooling here is stdlib `zipfile` plus targeted string edits.

**ElementTree reads; it never writes.** Round-tripping a pptx through it rewrites
the namespace prefixes and PowerPoint will not open the result.

## The round trip

Drop the file in `inbox/`. All three directories are gitignored — a client's
deck, and everything derived from it, stays out of the repo.

```bash
cd slides
python tools/deck_inbox.py intake "../inbox/Deras förslag.pptx"
```

That copies it to `work/<slug>/` and lays out everything needed to work on it:

| File | What it is for |
|---|---|
| `original.pptx` | Exactly as it arrived. Never written to again; it is the baseline the diff proves against |
| `deck.pptx` | The working copy — what the edit tools change |
| `deck.md`, `assets/` | The words, from `tools/pptx_to_md.py` |
| `inventory.json` | The handles, from `tools/pptx_inventory.py` |
| `before/*.png`, `before.pdf` | Every slide as PowerPoint draws it |
| `changes.md` | What we did, which goes back with the deck |

**Read `deck.md`, then look at the PNGs.** Both. The Markdown gives the words in
order; only the render shows what the slide is — a timeline, a pricing table, a
sign-off page — and whether text already overflows its box.

Then edit, then:

```bash
python tools/deck_inbox.py handback ../work/deras-forslag
```

which validates, diffs, re-renders, and writes `outbox/<their name> (Nexer).pptx`
with a PDF and a change note beside it. A deck with a hard problem never gets
that far.

## First decide which kind of deck it is

`inventory.json` answers this in one field, and it changes everything downstream:

```json
"kind": "template",  "layouts": [{"name": "Title and Content", "placeholders": ["title", "body"]}]
```

**`template`** — the layouts carry placeholders. Build a new slide on one, let
text inherit from the master, and use `<a:schemeClr>` so it follows the theme.
This is the advice you will find everywhere, and it is right for this case.

**`free-shape`** — no placeholder anywhere. A deck generated by PptxGenJS,
Gamma, Google Slides or a similar tool typically has exactly one empty layout
and a stock Office theme, with every colour written as literal `srgbClr`. There
is nothing to build on and nothing to inherit. **Reverse the usual advice:** copy
a neighbouring slide and reuse its hex values. A `schemeClr` here resolves to
stock Office blue and reads as obviously foreign.

`colour_use` confirms it. The client deck tested against reported 1225 `srgbClr`
against 4 `schemeClr`.

## Authoring a slide that looks native

**Clone, then rewrite. Do not start from an empty canvas.** The deck's own
slides are working examples of its design, already correct about the things that
are tedious to get right.

```bash
python tools/pptx_edit.py add ../work/x/deck.pptx --clone 8 --after 8   # a starting point
python tools/pptx_edit.py xml ../work/x/deck.pptx 9                     # read what you got
```

The other three verbs address by the ids in `inventory.json`:

```bash
python tools/pptx_edit.py text   deck.pptx --slide 13 --shape 4 --para 0 "Ny rubrik"
python tools/pptx_edit.py delete deck.pptx 17
python tools/pptx_edit.py move   deck.pptx 9 --to 6
```

`text` rewrites the paragraph as one run wearing the first run's properties,
which is what keeps their type size, weight and typeface. It refuses a
paragraph whose runs are genuinely formatted differently — a bold lead-in then
normal text — unless you pass `--flatten` and accept losing that. It ignores
the `err=` and `dirty=` attributes spell-checking scatters about, which is why
a paragraph PowerPoint has split into seventy runs still counts as uniform.

`delete` takes the notes page with the slide, and any media no other slide
still references. `move` rewrites only the running order, so no slide part
changes at all.

Take the grid and the palette from `inventory.json` rather than inventing them —
every shape carries its EMU geometry, preset shape, fill and per-paragraph run
formats. Reuse the deck's own left margin, its card width, its type sizes.

When the slide is more than a light edit, generate the XML with a short script
rather than typing it, and keep the script: geometry is arithmetic, and
arithmetic done by hand goes wrong silently.

```bash
python tools/pptx_edit.py add ../work/x/deck.pptx new-slide.xml --after 8
```

Five things to copy from a neighbouring shape rather than writing fresh:

- **`<a:ea>` and `<a:cs>` typefaces beside `<a:latin>`.** A missing `typeface`
  attribute on `<a:ea>` is a documented cause of the repair dialog that schema
  validators pass clean.
- **Child order.** `spPr` runs xfrm, geom, fill, ln, effects; `rPr` runs fill,
  latin, ea, cs; `txBody` runs bodyPr, lstStyle, then the paragraphs, with
  `endParaRPr` last. PowerPoint is order-sensitive where the schema says
  sequence.
- **One `<a:p>` per line.** Never concatenate two bullets into one paragraph.
- **`xml:space="preserve"`** on any `<a:t>` with a leading or trailing space.
- **Entities for quotes** — `&#x201C;` `&#x201D;` — since editing tools convert
  smart quotes to ASCII.

Then look at it. `handback` re-renders, but during authoring:

```bash
powershell -File tools/shoot_pptx.ps1 -Deck ../work/x/deck.pptx -OutDir ../work/x/after
```

Nothing measures text without rendering it, so overflow is only ever found by
looking.

## What the tools guarantee, and what they do not

`tools/pptx_edit.py add` makes all four registrations a slide needs — the part,
its `.rels` with exactly one `slideLayout` relationship, an `Override` in
`[Content_Types].xml`, a `Relationship` in `ppt/_rels/presentation.xml.rels`, and
a `<p:sldId>` in the `sldIdLst`. Missing any one is the repair dialog. It also
refuses malformed XML and any `r:embed` the rels cannot satisfy, without writing.

`tools/pptx_diff.py check` looks for the faults known to break a deck. Run it on
the file **as it arrives** too — the client deck tested against arrived with its
page numbers already wrong, and it is much better to tell them than to be blamed
for it.

`tools/pptx_diff.py diff original.pptx deck.pptx` matches slides by `sldId`, not
position, so inserting a slide does not read as the whole deck changing.

Not handled, deliberately:

| | |
|---|---|
| `p14:sectionLst` | Adding a slide does not put it in a section. `check` warns when a deck has sections |
| `docProps/app.xml` | Slide count left stale. PowerPoint recomputes it on save; pandoc ships `<Slides>0</Slides>` and opens fine |
| Page numbers typed as text | Cannot be fixed by inserting. `check` reports which slides disagree with their position |
| Speaker notes on a new slide | A clone's notes relationship is dropped — two slides sharing one notes page is a defect PowerPoint repairs |

## Three things that will bite

**Never reorder the children of `<p:presentation>`.** A PptxGenJS deck puts
`<p:notesMasterIdLst>` where the schema does not expect it. PowerPoint reads that
happily; tidying it kills the deck.

**Every path handed to COM must be absolute.** PowerPoint resolves a relative
path against its own working directory, and reports a directory missing seconds
after the script created it.

**Never save the deck through PowerPoint.** `SaveAs` rewrites every part, losing
the byte-identity the whole approach exists to give, and on a labelled deck it
can raise a modal prompt that never returns with nobody at the keyboard.
`shoot_pptx.ps1` only ever opens read-only and uses `SaveCopyAs`.

A file that arrived by email or download also carries Mark of the Web and opens
in Protected View, where it is not in `Presentations` at all. `Unblock-File` it
first. Decks in a synced OneDrive folder are worth copying out before working on.

## Verifying it

Tested on a 16-slide client deck on 2026-09-18, Windows 11, PowerPoint 16,
Python 3.12. Adding one authored slide after slide 8:

```bash
python tools/pptx_diff.py diff ../work/x/original.pptx ../work/x/deck.pptx
```

should report **all original slides byte-for-byte unchanged**, with only
`[Content_Types].xml`, `ppt/presentation.xml` and `ppt/_rels/presentation.xml.rels`
changed and nothing removed. Then PowerPoint must open it and report the new
count, and the before/after PNGs of the untouched slides must be pixel-identical:

```python
from PIL import Image, ImageChops
ImageChops.difference(Image.open(a).convert("RGB"),
                      Image.open(b).convert("RGB")).getbbox() is None
```

Map those by original position, not file number — an inserted slide shifts every
later one.

## Related skills

`nexer-slides` builds our own decks from Quarto and exports them through the
Nexer reference template; this skill is the other direction, for a deck we did
not build. `manual-testing` is the habit this depends on — the render is the
only oracle. `tdd` is how the tools were built, and `slides/tests/deckfixture.py`
writes a deck in memory in both PowerPoint's and pandoc's XML dialects, which is
the thing to extend when adding an edit.
